# P3：笔记关系图谱调研与实施计划

> 调研日期：2026-09-20；基线：`dev_tttt`、122 篇公开文章、143 个现有标签、32 个分类条目。
>
> 目标不是制作一张好看的“标签毛线团”，而是让读者在文章页正文之后、现有“相关推荐”之前，看到可解释、可点击、会随笔记增长的局部关系图；后续再提供全站探索入口。

## 1. 调研结论

[Obsidian 的关系图谱](https://obsidian.md/zh/help/plugins/graph)将笔记作为节点、内部链接作为连线；它同时提供局部图、深度、筛选、颜色分组和连线方向。对本站最值得复用的是**局部图优先**：读者已经在某篇文章内，先回答“这篇应接着读什么、它依赖/解释/对比什么”，比一次展示全站所有节点更有用。

本站当前 Butterfly 的“相关推荐”只按共同标签加权；同权重时采用随机次序。它不能表达“前置知识”“源码解读”“对比”“配套工具”等明确语义。现有标签中 `OpenFOAM` 有 37 篇、`网格` 17 篇、`CFD/OpenFOAM/网格` 17 篇，若把相同标签直接两两相连，少数通用标签会制造高密度团块，结果既不稳定也不可解释。

因此建议采用**混合关系图（hybrid graph）**：

1. 作者声明的文章关系是主边，拥有最高权重和可见的关系类型；
2. 已有 Markdown 站内文章链接是次级边，可自动收集，但要由审计报告提示作者确认；
3. 受治理的标签/分类重合只作弱边或候选推荐，绝不把每个同标签文章直接相连；
4. 语义相似度、AI 自动归类不进入第一期的公开图谱，只能作为将来人工确认的候选来源。

这保留了标签系统的长期价值，但不把标签系统误当成知识关系本身。

## 3. 推荐的数据模型

### 3.1 每篇文章的稳定身份与明确关系

新文章或参与图谱的存量文章逐步增加以下 front matter，不要求一次性改完全部 122 篇：

```yaml
graph:
  id: openfoam-mesh-quality-improvement
  relations:
    - target: bc-layer-calculator
      type: tool
    - target: mesh-induced-numerical-problems
      type: explains
    - target: snappyhexmesh-baffles
      type: extends
```

`graph.id` 为小写 ASCII kebab-case，一旦发布不改；文件名、标题、日期和 permalink 后续即使调整，关系仍可稳定解析。`target` 必须指向已存在且唯一的 `graph.id`。第一期支持的关系类型应保持少而清楚：

| type | 读者看到的含义 | 边方向 |
|---|---|---|
| `prerequisite` | 建议先读 | 先修知识 → 当前文章 |
| `explains` | 解释/展开 | 概念或总览 → 细节文章 |
| `extends` | 进一步推导或扩展 | 基础文章 → 扩展文章 |
| `compares` | 对比阅读 | 双向 |
| `tool` | 配套交互工具或脚本 | 文章 → 工具 |
| `series` | 同一系列导航 | 双向或由系列页发出 |

方向是阅读语义，不是等级；鼠标悬停和图例必须把类型文字说清楚，不能只用颜色传达含义。

### 3.2 受控标签词表，而非无限平铺标签

新增一个受版本控制的词表，例如 `source/_data/taxonomy.yml`，作为增量治理层：

```yaml
tags:
  openfoam:
    label: OpenFOAM
    aliases: [OF]
    kind: platform
    relation_weight: 0
  mesh:
    label: 网格
    kind: topic
    relation_weight: 1
  snappyhexmesh:
    label: snappyHexMesh
    kind: tool
    relation_weight: 2
```

- `label` 是页面可见名称；`aliases` 吸收旧写法，不必立即改写历史文章；`kind` 用于配色、过滤与统计。
- `relation_weight: 0` 的广义标签（例如 `CFD`、`OpenFOAM`、`CS`）仍可导航和检索，但不生成标签边。
- 标签相似只能作为图谱的弱候选：同一对文章最多一条弱边、至少共享两个非泛化标签、且每篇最多补充 2 条。首期也可完全不显示弱边。
- 分类继续承担层级归档；标签承担跨层主题。二者都不替代 `relations` 的作者意图。

## 4. 页面和交互设计

### 4.1 首期：文章局部图

在 `article#article-container` 内容末尾注入一个“笔记关系”区块，位于版权、标签、打赏、翻页和 Butterfly 的“相关推荐”之前。默认只渲染当前节点的一跳邻居（建议上限 12 个）；当前文章居中加粗，点击其他节点跳转文章或工具。若没有可用关系，整个区块不输出，不能显示空白框。

- 图例：按关系类型显示色块和文字；可只看某一类型。
- 交互：悬停高亮关联边；键盘可聚焦节点；点击后正常导航；提供“以列表阅读关系”的等价文本内容。
- 移动端：默认显示关系列表和“展开图谱”按钮；避免 force layout 占满首屏或妨碍滚动。
- 减少动态：尊重 `prefers-reduced-motion`；布局完成后停止模拟，不把动画作为内容本身。
- 无障碍/SEO：图是增强层，关系链接必须在静态 HTML 中以列表存在；JS、Canvas 或 SVG 失败时读者仍可访问关系文章。

### 4.2 后续：全站图谱页

在已有种子关系足够覆盖多个系列后，增加 `/knowledge/graph/`：按分类/受控标签/关系类型筛选，默认隐藏孤立节点和泛化标签边；提供搜索、图例、节点详情与“打开文章”。全站图不替代文章页的局部图，也不在首页自动加载。

实现库候选中，推荐在第二阶段评估 [Cytoscape.js](https://js.cytoscape.org/)：它提供节点/边样式、布局、筛选、触摸缩放与序列化 JSON，且可通过 npm 本地打包，不依赖第三方 CDN。首期若局部图只需十余节点，也可先以小型原生 SVG 实现，避免过早加入大依赖；不建议把 D3 force 的自定义布局作为第一项基础设施。

## 5. 构建与维护设计

1. 在 `scripts/note-graph.js` 编写 **Hexo 插件**（该目录只放 Hexo 插件，符合仓库约束）。它读取 `hexo.locals.get('posts')`、受控词表和 front matter，生成虚拟 `note-graph.json`，并以 `after_post_render` 添加静态关系列表与图谱容器。
2. 图谱数据按 `graph.id`、目标和类型稳定排序，保证相同输入有相同生成物；不把生成 JSON 或 `public/` 提交进仓库。
3. 将浏览器端 CSS/JS 放在受版本控制的 `source/js/`、`source/css/`，以两主题都可使用的方式加载；不修改 `node_modules`，不依赖外部 CDN。
4. 在 `tools/audit-source.mjs` 或独立 `tools/audit-note-graph.mjs` 增加机器检查：重复/缺失 ID、悬空 target、非法 type、自环、别名冲突、标签规范性、单节点异常高的弱边数。
5. 审计同时输出维护报告：不可解析的站内文章链接、指向不发布草稿的链接、零入/零出边的孤立节点、仅由泛化标签聚成的簇。前两项按链接策略报错或警告；后两项只报告，不能把“孤立”误判为错误。
6. 审计输出同时给出“可从站内链接推导的候选关系”，只报告、不自动写入 front matter；关系是编辑决策，不由脚本擅自发布。若将来引入 Wiki 双链，应先验证标题冲突、别名、代码块/公式块排除与草稿链接策略。

## 7. 验收与停止条件

- [x] 每个渲染的边都有明确来源：作者关系、已确认站内链接或在图例中明确标注的弱标签关系。
- [x] `npm run check:source` 与 `npm run verify` 通过；图谱审计对重复 ID、悬空 target、非法关系类型失败退出。
- [x] 页面未加载图谱脚本或 JavaScript 失败时，整个图谱模块隐藏；无关系的文章不显示模块。
- [ ] 文章页图谱默认不超过 12 个邻居，移动端不遮挡正文或相关推荐；不以随机布局位置表达任何语义。
- [x] 首期样本中没有由 `OpenFOAM`、`CFD`、`CS` 等泛化标签单独产生的可见边。
- [ ] 审计报告可定位每个不可解析站内链接与每个孤立节点；“孤立”只触发人工内容复核，不会被脚本自动连边或删除。

暂不做：自动根据全文向量建立公开边、全量旧文自动加 `graph.id`、用标签频率替代人工关系、在首页默认加载全站力导向图、把 Cosma 产物裁剪后嵌入 iframe、在公开站点运行 GraphRAG/模型服务。这些都会放大现有元数据噪声、构建复杂度或隐私暴露面，且难以向读者解释。
